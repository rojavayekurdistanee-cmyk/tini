# حماية بيانات المستخدم — دليل التطبيق

## ما الذي تغيّر؟

أصبح `users/{uid}` مستنداً خاصاً لا يستطيع قراءته من التطبيق إلا صاحب الحساب.
السيرفر يستخدم Admin SDK ويستمر في الوصول إليه. تبقى المحفظة والبريد والهاتف
وتاريخ الميلاد ورموز الإشعارات وإعدادات الأمان والسجل الشخصي في أماكنها الحالية.

أُنشئت مجموعة عامة `public_profiles/{uid}` تحتوي نسخة محدودة من بيانات العرض.
القائمة المسموحة مكتوبة صراحة في `functions/public_profiles.js`؛ أي حقل جديد
في مستند المستخدم يبقى خاصاً تلقائياً ما لم يُضف عمداً إلى القائمة العامة.

هذا اختيار مقصود لتجنب نقل الأرصدة أو تغيير مسارات المعاملات المالية: نحمي
المستند الأصلي كله ونفصل عنه نسخة العرض العام. لا توجد عملية تصفير أو إعادة
حساب أرصدة. لا تغييرات على وظائف الشراء أو استرداد الدفعات أو العرش أو الصناديق.

## البيانات العامة والخاصة

- العامة: الاسم، اسم المستخدم، الصورة، النبذة، تاريخ إنشاء الحساب، العدادات،
  رقم التاج، الشارة، بيانات التتويج، إعدادات الجمهور وإعدادات الخصوصية التي
  يحتاجها الزائر لتحديد ما يمكن عرضه أو إرسال طلب له.
- حالة النشاط ووقت آخر ظهور يُنسخان فقط إذا لم يوقف المستخدم عرض النشاط.
- الخاصة: الرصيد والحجوزات والديون ورمز حساب المشتريات وإصدار المحفظة والبريد
  والهاتف وتاريخ الميلاد ورموز الإشعارات وإعدادات الأمان وقوائم الحظر وسجل البحث
  وأي حقول أخرى غير موجودة في القائمة المسموحة.
- تاريخ الميلاد يبقى متاحاً لصاحب الحساب للتحقق من عمر المشاهد؛ حساب جمهور
  الآخرين يستخدم أعلام الجمهور العامة، ولا يحتاج تاريخ ميلادهم.
- المجموعات الفرعية تحت `users` تحتفظ بقواعدها الخاصة. هذا التعديل لا يدّعي
  تدقيق أمان جميع مجموعات المشروع أو جميع القواعد الأخرى.

`lib/user_documents.dart` يختار المستند الخاص للحساب الحالي والعام للحسابات
الأخرى، ولا يحاول الرجوع إلى مستند خاص عند غياب البروفايل العام. استعلامات
البحث والقوائم انتقلت إلى `public_profiles`. القواعد تمنع كتابة هذه المجموعة
من العميل، حتى من صاحب الحساب.

## المزامنة والحظر

الدالة `syncPublicProfile` تتابع تغيّر مستند المستخدم وتقرأ حالته الحالية داخل
معاملة؛ وصول أحداث قديمة أو تكرارها لا يعيد بيانات قديمة أو حساباً محذوفاً.
تستبدل البروفايل العام بدلاً من دمجه لإزالة أي حقول لم تعد مسموحة. تغيّر الرصيد
وحده لا يكتب البروفايل العام من جديد. يوجد استدعاء للدالة وقراءتان داخليتان
للتحقق عند تغيّر المستند؛ هذا ليس وعداً بتقليل تكلفة Firestore.

المزامنة غير متزامنة، وقد يتأخر ظهور تغييرات البروفايل العام قليلاً. أخطاء الدالة
تُعاد محاولتها. راقب الأخطاء بعد النشر، وأعد تشغيل أداة التجهيز عند الحاجة.

قوائم الحظر لم تعد تُنشر. فحوص الحظر تستخدم `users/{myUid}/blockedBy` الخاص
بالمشاهد. أداة التجهيز تنشئ المؤشرات الناقصة من قوائم الحظر القديمة والمجموعات
الفرعية، دون نشر القوائم أو تعديلها. التطبيق الحالي ينشئ ويحذف هذه المؤشرات
عند الحظر وإلغائه كالسابق.

## ترتيب التطبيق على Firebase — لم يُنفّذ في هذه المهمة

**رفع الفرع إلى GitHub لا يفعّل حماية Firebase وحده.** الخطوات التالية تنفيذ
لاحق على المشروع الحقيقي، بعد مراجعة الفرع والاختبار. لا تنشر ملف القواعد أولاً:
الإصدارات القديمة تقرأ بروفايلات الآخرين من `users` وستتلقى permission-denied
بعد تفعيل القواعد الخاصة. لا توجد طريقة لإخفاء حقول المستند مع إبقاء القراءات
القديمة للمستند نفسه متاحة. نسّق تحديث التطبيق/حدّه الأدنى قبل الإغلاق النهائي.

1. خذ نسخة احتياطية إدارية لقاعدة البيانات وسجّل نسخة القواعد المنشورة الحالية.
   راجع مشروع Firebase الفعلي وتأكد أنه `titi-star0`. شغّل الأوامر من جذر المستودع.
2. ثبّت تبعيات وظائف السيرفر باستخدام `npm ci --prefix functions`.
3. انشر **الدالة الجديدة فقط**، وليس كل الوظائف ولا الفهارس:

   ```bash
   firebase deploy --project titi-star0 --only functions:default:syncPublicProfile
   ```

   الدالة تستخدم قواعد وصول Admin SDK، ولا تحتاج جعل المجموعة قابلة للكتابة
   من التطبيق. تبقى قواعد `users` المنشورة القديمة حتى خطوة الإغلاق النهائي.
4. جهّز اعتماد Admin SDK المحلي بطريقة آمنة بصلاحيات المشروع، مثلاً Application
   Default Credentials. تسجيل الدخول في Firebase CLI وحده لا يضمن اعتماد Admin
   SDK. لا تحفظ مفاتيح الخدمة أو تقارير الحسابات في المستودع.
5. شغّل أداة الفحص للقراءة فقط:

   ```bash
   node functions/backfill_public_profiles.js --project=titi-star0
   ```

   تعرض أعداداً فقط، ولا تطبع البريد أو الرصيد أو رموز الشراء. `mismatches` هو
   عدد البروفايلات الناقصة/المختلفة، و`missingReverseBlocks` مؤشرات الحظر الناقصة.
6. جهّز النسخ العامة ومؤشرات الحظر القديمة:

   ```bash
   node functions/backfill_public_profiles.js --project=titi-star0 --apply
   ```

   الأداة لا تكتب مستندات الحسابات الأصلية أو المحافظ أو العمليات أو حالة العرش
   أو حجوزات الصناديق. تكتب النسخ العامة ومؤشرات الحظر الناقصة فقط، وتزيل النسخ
   العامة اليتيمة بعد إعادة التحقق من حذف مصدرها داخل معاملة. يمكن إعادة تشغيلها.
7. أعد أمر الفحص من الخطوة 5. قبل الانتقال يجب أن تصبح `mismatches` و`orphans`
   و`missingReverseBlocks` صفراً. عند تغيّر حسابات أثناء الفحص، أعده بعد اكتمال
   المزامنة. عالج أخطاء الدالة/الأداة قبل متابعة الخطوات.
8. اختبر نسخة التطبيق الجديدة على حسابين ثم وزّعها/طبّق الحد الأدنى للإصدار:
   البحث، البروفايل، الصور، المحادثات، المنشن، المجموعات، المتابعة والحظر وإلغاؤه،
   إعدادات البريد/الهاتف وتاريخ الميلاد، إخفاء حالة النشاط، المحفظة والعرش والصناديق.
   اختبر تبديل الحسابات أيضاً: الاسم والصورة يأتيان من النسخة العامة، أما بريد
   تسجيل الدخول فلا يُقرأ من مستند حساب آخر؛ إذا غاب البريد المحفوظ محلياً قد
   يحتاج المستخدم إلى تسجيل دخول عادي مرة أخرى بدلاً من استرجاع البريد علناً.
   راقب المزامنة عند تعديل الاسم والصورة وإعداد الجمهور. لا تُجرِ مشتريات حقيقية
   لمجرد اختبار هذا التعديل؛ اختبر تدفقات المال في بيئة الاختبار الخاصة بالمتجر.
9. بعد جاهزية العملاء والبروفايلات، انشر قواعد Firestore فقط:

   ```bash
   firebase deploy --project titi-star0 --only firestore:rules
   ```

   هذا الأمر لا ينشر الفهارس. راجع فرق القواعد مع النسخة المنشورة قبل تنفيذه؛
   المستودع لا يثبت أن القواعد المحلية مطابقة للإنتاج. تحقق بحساب ثانٍ/عميل غير
   مسجل أن `users/{uid}` ممنوع، وأن `public_profiles/{uid}` لا يحتوي حقولاً خاصة.
10. راقب الأخطاء بعد الإغلاق. لا تعِد `allow read: if true` على `users` كحل سريع؛
    ذلك يعيد كشف البيانات. احتفظ بالقواعد الخاصة وأصلح قراءات العميل/المزامنة.
    لا حاجة لحذف ملف محفظة أو نقل/إعادة إنشاء رصيد. لا يمكن سحب بيانات سبق أن
    حُمّلت إلى أجهزة الآخرين قبل تفعيل الحماية؛ القواعد تضبط القراءات القادمة.

الأداة ترفض مشروعاً حقيقياً مختلفاً عن `.firebaserc`، ولا تتصل بالمحاكي إلا عند
استخدام loopback ومشروع يبدأ بـ `demo-`. لا تستدعِ أداة `migrate_wallets.js` القديمة
لتطبيق هذا التعديل؛ هذه ليست عملية انتقال محفظة.

## الاختبارات

```bash
npm ci --prefix functions
npm --prefix functions run test:profiles
firebase emulators:exec --project demo-tini-profile-privacy \
  --config firebase.privacy-tests.json --only firestore \
  "npm --prefix functions run test:privacy:emulator"
```

تحتاج Firebase CLI وJava 21 أو أحدث للمحاكي. اختبارات المحاكي ترفض التشغيل على
Firebase الحقيقي. تغطي القراءة لصاحب الحساب، منع الآخرين وغير المسجلين، البحث
العام، منع الكتابة على النسخ العامة وحقول المحفظة، الإعدادات الخاصة، المجموعات
الفرعية، سلامة الأرصدة والحجوزات ورمز الشراء أثناء التجهيز وإعادة التشغيل، الحظر
القديم، إزالة الحقول القديمة، إخفاء حالة النشاط وحذف البروفايل عند حذف مصدره.

التحقق المحلي لا يغني عن تجربة نسخة التطبيق على أجهزة الاختبار أو مراجعة
القواعد المنشورة فعلياً؛ لم تُجرَ تغييرات على مشروع Firebase الحقيقي هنا.
